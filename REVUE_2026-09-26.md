## 3. Ce qui ne va pas ou qui manque

### 3.1 — BLOQUANT : un run interrompu n'enregistre rien de ce qu'il a téléchargé

- **Constat (log du 26/09, stats Scrapy, base)** : 13 pages de liste puis ≈ 800
  fiches détail reçues (813 réponses 200), `item_scraped_count = 3`,
  `pmmp/db_upserts = 3`. Les 3 consultations enregistrées sont les **3 fiches en
  échec** (`dce_statut = echec_fiche_detail`, données de liste seulement). **Aucune
  des ≈ 800 fiches téléchargées avec succès n'est en base.** Le log affiche
  « scraped 0 items » pendant 42 minutes.
- **Cause (code)** : `spiders/pmmp.py` l. 34-36 et 358-360. Une fiche qui a des
  liens DCE n'est pas enregistrée tout de suite : elle programme une requête DCE de
  priorité `-5`, inférieure aux fiches (`0`). Scrapy traite donc les 1 200 fiches
  d'abord, les DCE ensuite, et la consultation n'est enregistrée qu'**après** son
  DCE. Tout arrêt avant la phase DCE (circuit breaker, fin de fenêtre à 10:00, PC
  éteint) perd tout le travail. Les pages brutes restent sur disque, mais aucun
  outil ne les réinjecte.
- **Conséquence** : demain, les mêmes 1 200 consultations seront de nouveau
  « nouvelles » et retéléchargées. Si l'interruption se reproduit, la base ne se
  remplira jamais.
- **Correction proposée** : enregistrer la consultation dès la fiche détail lue
  (statut DCE « en attente »), puis mettre à jour `dce_paths`/`dce_statut` après
  le téléchargement ; ou donner aux requêtes DCE une priorité supérieure aux
  fiches, pour que chaque consultation soit terminée avant la suivante. Ajouter un
  test : circuit breaker en milieu de run → les fiches déjà lues sont en base.

### 3.2 — GÊNANT : l'incident de ce matin peut se reproduire

- **Constat** : 3 coupures de connexion d'affilée (`ConnectionLost`) côté
  serveur, sur 3 fiches différentes, après 42 min et ≈ 800 requêtes à rythme
  régulier. Sans erreur HTTP (ni 403, ni 429).
- **Avis honnête** : un seul run automatique existe, je ne peux donc ni affirmer
  ni exclure la récidive. La régularité (coupure groupée après un volume donné)
  est compatible avec une limite côté portail (durée de session, volume par
  client) comme avec un incident réseau ponctuel. **Ce n'est pas rassurant par
  défaut** : avec le défaut 3.1, une récidive quotidienne signifierait zéro donnée
  collectée.
- **Correction proposée** : observer les runs des prochains jours avant de
  conclure ; si la coupure revient vers le même volume, réduire `PMMP_MAX_ITEMS`
  (ex. 600) plutôt que d'augmenter la tolérance du circuit breaker.

### 3.3 — GÊNANT : textes doublés en base (lieu d'exécution, objet)

- **Constat (base)** : `lieu_execution` est doublé dans les **23** consultations
  (« SALE SALE », « RABAT, NOUACEUR RABAT, NOUACEUR »). L'objet est doublé
  (« texte tronqué … texte complet ») dans les 3 consultations issues de la seule
  liste. Visible dans l'interface.
- **Cause (page brute archivée)** : le portail affiche la valeur, puis la répète
  dans une info-bulle cachée (`lieuxExecutions` puis `lieuxExecutionSuite`,
  `class="info-bulle"`). `pick()` (`parsers.py` l. 214 et 335) lit tout le texte
  du bloc et concatène les deux.
- **Correction proposée** : ne lire que la valeur visible (ou seulement
  l'info-bulle pour le texte complet), avec un test sur une page réelle de
  `fixtures/live/`. Les données déjà en base se corrigeront au run suivant qui
  relit les fiches.

### 3.4 — GÊNANT : raison d'échec illisible dans l'interface

- **Constat** : la carte « Dernière collecte » du tableau de bord affiche les
  **974 caractères** de `collecte_runs.raison` (3 URL et 3 traces Twisted), ce qui
  étire la carte sur toute la hauteur de l'écran. C'est ce que verra le chef de
  projet aujourd'hui.
- **Correction proposée** : dans l'interface, afficher un résumé (« Arrêt de
  sécurité : 3 erreurs de connexion consécutives ») et le texte complet dans un
  bloc repliable ; ou, côté collecteur, écrire `raison = circuit_breaker` et le
  détail ailleurs.
